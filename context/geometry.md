# Parametric geometry (2D and 3D)

`gecko_core::parametric::ParametricGeometry` generates an ordinary `Geometry` from
`data/geometries/*.param.toml`. The scorer, layout fitting, comfort tables, run hashes,
CLI and server use the resulting keys exactly as they use explicit `[[key]]` boards.
Existing geometry files and JSON shapes are unchanged.

Load a parameter file directly, e.g.

```
gecko compare -g data/geometries/corne-36.param.toml --json
gecko compare -g corne-36.param --json
```

`Store::geometry("name")` prefers `name.toml`, then `name.param.toml`. Listing geometries
returns the base name once, so a parameter-only board appears in the web picker and adding
a parameterized equivalent never changes an existing board selection. A direct path or
`name.param` selects parameters explicitly. Store resolves `[comfort]` CSVs after generation.
For custom saved runs, use a new model name matching its file's base name; `verify` reloads
geometry by the recorded name, as it does for explicit board files.

## Shape and metadata

A board has named `[[zone]]`s, ordered logical `rows`, and `[[zone.column]]`s. Separate
finger and thumb zones let the thumb cluster move without moving the finger matrix.
Units are u (19.05 mm); angles are degrees, positive clockwise in the x-right/y-down plane.
Without the 3D fields below, generated keys have z = 0 and x/y rotation = 0.

| Field | Meaning / default |
|---|---|
| Zone `anchor` | First column's first-row **center**, before stagger; `[0,0]` |
| Zone `rotate` | Rotate the whole zone about its anchor; 0 |
| Zone `rows` | Strictly increasing logical row labels, e.g. `[0,1,2]` or `[3]` for thumbs |
| Zone `row_pitch` | Distance between successive rows, independent of labels; 1 |
| Zone `home_row` | Logical home-row label; 1 (no home keys if absent from `rows`) |
| Zone `home_stretch` | Tag home-row stretch keys as home too; false |
| Zone `col_start` | First logical column label; 0 |
| Zone `mirror` | Generate a right-hand copy using `[split]`; false |
| Column `spread` | Baseline distance from previous column; 1; ignored for first column |
| Column `stagger` | Shift the column toward the user; 0 |
| Column `splay` | Rotate about this column's home-key center; 0 |
| Zone `arc_radius` | Bend the baseline into a circular arc; omitted = straight |
| Column `finger`, `effort` | Finger and one nonnegative base effort per logical row |
| Column `size`, `stretch` | Key footprint `[1,1]`, stretch flag false |
| Column `fill`, `mirror_fill` | Optional fill on the original / mirrored key |

The columns' total baseline distance is arc length: for distance `d` and signed radius
`r`, the baseline is `(r sin(d/r), r(1−cos(d/r)))`, with tangent angle `d/r`. Stagger and
row offsets follow that tangent; column splay adds rotation around the home key. Negative
radius curves away from the user. This is a real circular thumb arc, with independent
cluster position and rotation. A zone without a home row uses its first row as the splay
pivot while leaving every key's `home` flag false.

`[split]` has required `axis` (mirror plane x), plus `spread = 0`, `angle = 0`,
`pivot = [0,0]`. After zone transforms, the left hand rotates `−angle/2` about `pivot`;
the right copy reflects its centers as `x_right = 2*axis + spread − x_left`. Thus the
included hand angle is `angle`, and spread adds separation to the right half. Column
fingers in mirrored zones must be left-hand fingers; `LP↔RP`, `LT↔RT`, etc. are automatic.
An unmirrored zone can use either hand and receives only its own zone transforms.

For example, a two-thumb arc (add it beside a finger zone) is:

```toml
[[zone]]
name = "thumbs"
anchor = [3.5, 4.2]
rows = [3]
mirror = true
arc_radius = -5.0
rotate = 10.0
[[zone.column]]
finger = "LT"
effort = [1.0]
fill = "space"
mirror_fill = "enter"
[[zone.column]]
finger = "LT"
spread = 1.0
effort = [1.3]
fill = "tab"
mirror_fill = "bspc"
```

Column labels increase left-to-right in the unrotated topology: original columns first,
then mirrored columns in reverse. Keys sort by `(row,col)` across zones, preserving layout
row order even after splay or split rotation. Zones sharing a row need distinct `col_start`
ranges. Poses rotate key centers; the stored `pos` subtracts half of each key's size to match
GECKO's top-left convention. Computation uses f64, casts once to f32 and canonicalizes zero.

Unknown fields, non-finite values, invalid sizes/efforts, duplicate logical slots, invalid
fills and excessive key counts fail. Generation does not repair physical key collisions;
collision constraints belong to the geometry search (#39).

## 3D shape

Optional fields bend and tilt a zone into a Dactyl-style keywell. All default to 0; a board
using none of them is generated by the flat path, bit for bit as before.

| Field | Meaning |
|---|---|
| Zone `row_curve` | Degrees between successive rows (Dactyl α). Rows sit on an arc through the home row with the keycap tops `row_pitch` apart (chord), each key tilted to face the arc's axis: a concave column. |
| Zone `col_curve` | Degrees between successive columns (Dactyl β). Column `spread` becomes the chord between neighbouring keycap tops; equal spreads lie on a circle. Not with `arc_radius`. |
| Zone `center_col` | Column index (fractional allowed) left level by `col_curve` |
| Column `lift` | Column height, u (Dactyl's per-column z offset; `stagger` is its y offset) |
| Zone `tent`, `tilt`, `lift` | About the anchor after `rotate`: raise the +x side, raise the far edge, height |
| Split `tent`, `tilt`, `lift` | Both halves (mirrored): raise the inner edges, raise the far edges (negative = negative slope), height |

Order: row arc (in the column), column arc, column splay, zone `rotate` → `tent` → `tilt`,
then the split's angle → tent → tilt about `pivot`, then the mirror. 3D boards are computed
on the keycap top centre (`pose::CAP_HEIGHT` = 0.42 u above `pos` z) and stored as ordinary
`pos`/`rot`; a 3D zone's tops start at z = `CAP_HEIGHT`, so `pos` z = 0 at zero lift.

**Rotation convention** (`gecko_core::pose`, shared with the viewer): `rot = [rx, ry, rz]`
is the matrix `Rx(rx) · Rz(rz) · Ry(ry)` in board axes (x right, y toward the user, z up),
i.e. tent first, then splay, then tilt; three.js draws it as Euler XYZ over `(rx, −rz, ry)`.
`+rx` turns the keycap top toward the user, `+ry` raises the key's +x side, `+rz` turns it
clockwise from above. Mirroring negates `ry` and `rz`.

**Metrics on 3D boards** (`Geometry::metric_points`): geometric metrics (B03/S03 distance,
B14/S04/S05/T09 stretch, B10 row jump, Y03 order) measure between keycap tops expressed in
each hand's frame (best-fit plane of its finger keys; x = board x and y = toward the user
within the plane, z = the normal). Distances are true 3D fingertip distances; "sideways" and
"forward" are what the hand sees on a tented half. A rigid tent changes no metric
(`tests/three_d.rs`). Flat boards use `pos` exactly, so their scores are unchanged.

`tests/fixtures/dactyl-well.param.toml` is the Dactyl-Manuform 5x6 finger keywell in this
format (row pitch 18.4 mm, spread 19.9 mm, α 15°, β 5°, centre = pinky column, 15° split
tent); it reproduces the bundled `dactyl-manuform-5x6` keys up to where each half sits.

## Bundled models and search

`ortho-30.param.toml` and `corne-36.param.toml` reproduce their explicit files exactly,
including metadata, content hashes and all reference scores under all bundled profiles.
Corne targets the corrected QMK flat projection, with a taller inner thumb and one thumb
column stagger. Its baseline omits `arc_radius`: QMK display coordinates do not establish
a measured circular thumb arc. A physical thumb arc can be selected explicitly.

The useful symmetric search vector is about 16 numbers: five column staggers, five splays,
split spread/angle, thumb x/y/rotation/radius. Row/column pitches can also be freed. Finger
assignments, efforts, logical rows, fills and footprints are metadata, not independent key
poses. `ParametricGeometry` is serializable; `gecko geometry optimize` searches these parameters
([algorithms/geometry-search.md](algorithms/geometry-search.md)).
`generate_unchecked` skips the overlap check so colliding candidates can be scored. 3D adds row/column curvature, column lifts and split tent/tilt. The resolved `Geometry::hash()` identifies generated
input content, so equivalent explicit and parametric boards remain interchangeable in runs.

## Collision (G04)

`Geometry::collisions(margin)` (`collision.rs`) lists overlapping keycap pairs on flat boards:
each physical key's footprint as an oriented box (centre, size, z rotation) grown by `margin`
u per side, candidate pairs from a uniform grid (cell = the largest box diagonal), and the
separating axis test shared with `flat2d` for the penetration depth. Overlaps ≤ 0.001 u count
as touching. `Geometry::validate` (TOML load, KLE import, parametric generation) rejects any
overlap at margin 0; `check_keys` holds only the structural checks and is what layer expansion
and `Scorer::set_geometry` use, so search candidates that collide can still be scored and
penalized by depth. Layer copies share their physical key and are skipped. Non-flat boards
return no collisions: tilted and tented keycaps need 3D volumes (H8, #66). Every bundled flat
board is collision-free.

`Geometry::collisions_3d(margin)` is the approximate 3D test the geometry search uses on
non-flat candidates until H8: per key a keycap frustum (footprint + margin at the bottom, inset
`CAP_TAPER` 0.15 u per side at the top, `CAP_HEIGHT` tall, like an SA/DSA cap) and an MX switch
body below it (0.78 u square, 0.45 u deep), each pair tested with the full separating axis
theorem (face normals and edge × edge axes); depth is the deepest overlap. It finds the same
pairs as the 2D test on flat boards, and every bundled board (Dactyl included) is clear.
`validate` still checks 2D only.

## Derived effort and stretch (G4)

New boards need no hand-entered costs (`derive.rs`, `Geometry::derive_missing`). Distances are
between key centres in each hand's measuring frame (`metric_points` + half the key size), so
3D boards measure along their surface.

- **Effort** (a reach proxy until the hand model replaces M01's base effort):
  `HOME_EFFORT[finger] + TRAVEL[finger] · d`, d = distance (u) to the finger's non-stretch home
  key. Home 1.6 / 1.3 / 1.1 / 1.0 (pinky → index, the bundled values); travel 1.14 / 1.15 /
  1.03 / 1.08 per u, a least-squares fit to the seven bundled flat boards (r = 0.93, RMSE 0.28;
  a d² term gained nothing). Thumbs: 1.0 + 0.5 per u from the thumb key nearest the rest point
  0.5 u inward and 2.3 u below the index home key (unless a thumb key is marked `home`). A
  finger without a home key measures from its hand's nearest home key. Missing efforts in a
  board file are NaN until `from_toml` fills them; parametric columns without `effort`
  re-derive on every `generate`, so efforts follow keys during a geometry search.
- **Stretch**: an index key more than 0.625 u inward of the index's outermost home key (between
  ANSI's `V`, 0.5 u, and `T`, 0.75 u). Derived only when a board file marks no key `stretch`
  at all. It reproduces every bundled board's flags except ANSI's `N`, which the file labels
  stretch by column although it sits 0.5 u from `J`, like `V` from `F`.
- **Travel (G02)**: B03/S03 already measure Euclidean distance between metric points (with the
  `sfb.lateral` multiplier), not grid steps, so they follow moved keys.

Check (`tests/derive.rs`, english / default, nothing hand-entered): a 30-key grid with Corne's
column stagger (pinky 0.3, ring 0.1, index 0.1, stretch 0.2 u) beats ANSI row stagger for
Colemak-DH (−1.9), Graphite (−0.7), Semimak (−1.2), Sturdy (−0.3) and Dvorak (−0.9). QWERTY is
the exception (+0.56): its bottom-row bigrams were laid out for row stagger and stretch more
(B14 12.7 vs 11.9) without it. A plain ortho grid also beats ANSI for every layout but QWERTY
(+0.04); stronger stagger (pinky 0.5, ring 0.125, index 0.25) helps Colemak-DH and Dvorak more.
